- **Member A (`feat/member-a-triage-providers`):** Implemented the deterministic fallback mapping to ensure CI builds never fail when an unrecognized or misconfigured provider string is passed, defaulting strictly to `SimulatedTriage`.
- **Member B (`feat/member-b-llm-ollama-triage`):** Integrated live cloud providers (`groq`, `llm`, `ollama`) and raised an explicit `ValueError` when an unknown provider was requested to catch misconfigurations early.

## 3. Resolution Applied

The conflict was resolved cooperatively by combining both intents:
1. Supporting all live cloud providers (`groq`, `llm`, `ollama`, `rules`, `simulated`) as dynamic singletons.
2. Logging a warning and falling back to `SimulatedTriage` for unrecognized strings, ensuring automated CI runs and load tests never crash with unhandled 500 server errors due to environment variable typos.

```python
    normalized_name = (provider_name or "").strip().lower()
    if normalized_name not in PROVIDER_REGISTRY:
        logger.warning(
            f"Unknown triage provider '{provider_name}'. Falling back to 'simulated'. "
            f"Supported providers: {list(PROVIDER_REGISTRY.keys())}"
        )
        return SimulatedTriage()

    provider_cls = PROVIDER_REGISTRY[normalized_name]
    return provider_cls()
```

## 4. Why This Version Won (2–4 Sentences Rationale)

1. Member A's fallback strategy won for the error-handling branch because production resilience mandates that municipal complaint intake must never crash or reject citizen submissions due to a minor configuration string typo.
2. Member B's dynamic registry normalization won for the resolution logic, enabling clean support for aliases (`groq`, `llm`, `ollama`, `rules`, `simulated`) without duplicate instantiation blocks.
3. This hybrid resolution satisfies both architectural requirements: graceful degradation under fault conditions (Rubric C1, F3) and strict extensible provider dispatch (ADR 0001).
